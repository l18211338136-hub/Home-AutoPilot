## HomeFly：补齐真正的飞行日志（Blackbox）

- 用户指出「飞行日志需要做」——原项目只有 `FlightDataRecorder` 内存通道 + `CountingBinarySink` 计数器，不落盘。已把黑匣子做成真实交付：
  - `src/platforms/common/logging/flight_log.hpp/.cpp`：自描述 `.hfl` 格式，64 B Header（magic/version/record_size/session_id/control_period_us/config_hash/platform）+ N×72 B 记录 + 32 B Footer（记录数/丢帧/写失败/FNV-1a 校验和）；`FlightLogWriter` 实现 `ILogSink`，攒 16 条一块批量写，`drain_to()` 的失败保留语义自动给重试。
  - `flight_log_storage.hpp` 定义平台工厂（`open`/`storage`/`close`），链接期绑定；Linux `file_log_sink.cpp` 真实 `fopen/fwrite`，ESP32/STM32 `flight_log_sink.cpp` 用四个 `hf_flight_log_*` BSP C 钩子（宏守卫，host 构建为空 TU）。
  - `main.cpp`：真实 `std::thread` 低优先级任务同时驱动 `log_drain(8)` 与 `flight_log.pump()`，控制循环零 I/O；`--flight-log PATH` / `--no-flight-log`；`tools/hfl_dump.py` 离线校验 + CSV + `--strict`。
  - `SKILL.md` 新增「飞行日志（Blackbox）」规范段与第 17 条铁律，用户级副本已同步一致；新增 `docs/flight_log.md`，其余文档全量对齐。
- **顺手修的既有 bug**：`flight_controller.cpp:78` 的 `validate_imu(sample, now_us)` 用的是 `IImu::read()` **之前**的时间戳，任何真实时钟下都会把 IMU 数据误判为「来自未来」→ 首帧 `ImuTimeout` Failsafe。改为 read 之后取 `validation_now_us`，虚拟时钟下行为不变，`--realtime` 首帧恢复正常。
- **非确定性丢帧坑**：host 全速仿真几毫秒跑完 2000 周期，后台线程可能抢不到 CPU，实测重复运行时 `dropped` 在 0~610 间波动。已在 `main.cpp` 加**仿真专属有界背压**（环占用过半时 `yield()`，10 万次上限），真机不需要这句。修复后连续 5 次 2000 步与 20000 步长跑全部 `dropped=0`、checksum 可复现。
- 最终验证：干净构建 56/56 目标、CTest 11/11（73 用例，新增 `test_flight_log.cpp` 10 项）、MSVC `/W4` 零警告；`HF_LOG_COMPILE_MIN_LEVEL=2` 变体 11/11。实际生成 `homefly_flight.hfl`（144096 B，2000 条/125 块/dropped=0），`hfl_dump.py --strict` PASS，`build/linux/flight_demo.csv` 2000 行。
- 边界：ESP32-S3 / STM32 后端仍是 BSP 占位；`--realtime` 在通用 OS 上会因 1 ms 抖动触发 `ControlOverrun` 粘性 Failsafe（既有保护机制的正确行为），该模式只用于观察真实节拍下的日志行为，不用于判定控制收敛；断电最多丢当前块 16 ms 且 Footer 缺失。
- MSVC 的 `fopen` C4996 通过在根 `CMakeLists.txt` 加 `_CRT_SECURE_NO_WARNINGS`（仅 MSVC）消除，保持 `/W4` 零警告。

## 调研：Windows 上跑 Gazebo 的可行性（影响 SITL 拓扑选型）

- 官方现状（gazebosim.org/docs/latest/getstarted，2026-11 查）：Ubuntu 22.04/24.04/26.04 与 macOS 为正式二进制分发；**Windows 仅 Gazebo Jetty via conda-forge + Pixi 的「实验性」支持，官方注明 known runtime issues**；Harmonic 文档写死「Conda-Forge 支持 not fully functional」，且 Harmonic 需把 server(`gz sim -s`) 与 GUI(`-g`) 分两个终端启动；Ionic 只有 Windows 源码编译指引（pixi/conda + VS + colcon，标注 experimental）。Gazebo Classic 11 无官方 Windows 二进制。
- **对本项目最关键的坑**：WSL2 NAT 模式的 `localhostForwarding=true` 默认只转发 TCP，**UDP 的 127.0.0.1 跨 Windows↔WSL2 边界不通**（microsoft/WSL#8868、#8783，多年未修；mirrored 模式 + `hostAddressLoopback=true` 可缓解但不稳定，`netsh portproxy` 仅 TCP）。HomeFly SITL 全是 UDP 帧，所以「飞控跑 Windows + 桥接/Gazebo 跑 WSL2 且都用 127.0.0.1」必然失败。
- 可行拓扑：①**全放 WSL2 Linux 侧**（Gazebo + 桥接 + 飞控同一网络命名空间，参数不用改，最推荐；根 `CMakeLists.txt` 非 MSVC 分支是 `-Wall -Wextra -Wpedantic`，`udp_socket.cpp` 有 POSIX 分支，但只在 MSVC 验证过，首次 GCC 编译需实测）；②**全 Windows 原生**（Pixi 装 Jetty + 现有 exe + Python 桥接，规避跨边界 UDP，但实验性 + `gz-transport-python` 绑定齐全度未验证）；③混合模式必须用双向显式 IP：桥接 `--host <Windows主机IP>`、飞控 `--gazebo-host <WSL2_IP>`，Windows 防火墙放行 UDP 14550 入站、Hyper-V 防火墙放行 14551，且飞控已绑 `INADDR_ANY`（`udp_socket.cpp:123`），可行但脆弱。
- SITL 建议用 `gz sim -s`（headless server-only），绕开 Windows 实验版 GUI/OGRE2 的已知问题。
- 本机 `wsl.exe` 被安全策略程序黑名单拦截，无法代为检测/安装 WSL；Gazebo 实际安装需用户自行执行或在解除黑名单后进行。
- **为 WSL2 落地补的构建修复**：`main.cpp` / `gazebo_transport.cpp` / `linux_timer.cpp` 用了 `std::thread`，但 CMake 从未显式链接线程库（MSVC 无感，Linux 老 glibc 会 `undefined reference to pthread_create`）。根 `CMakeLists.txt` 加 `find_package(Threads REQUIRED)`，`simulation/CMakeLists.txt` 用 `PUBLIC Threads::Threads` 传递给 app。Windows 复验 `Found Threads: TRUE` + 13/13 CTest 通过、无需重编译（MSVC 下该 target 为空）。
- 给用户的 WSL2 部署要点：项目**必须重新编译成 Linux 原生 ELF**（现有 `.exe` 是 Windows PE，WSL interop 启动后仍是 Windows 进程，UDP 命名空间不在 Linux 侧，会退回混合模式）；源码建议放 WSL2 ext4（`~/Home-Fly`）而非 `/mnt/d`（DrvFS 小文件 I/O 慢、可执行位/换行问题）；先跑 `--backend mock` 验证链路，再接 `--backend gz`（适配桩需按 Gazebo 版本补话题名，`homefly_quad.sdf` 只是模型片段需放进 world）。

## HomeFly：配齐 WSL2 SITL 部署件（用户「配」）

- **修掉两个会让真 Gazebo 完全跑不通的既有 bug**（`tools/gazebo_bridge.py`）：① `run_gz.on_imu()` 的 `state["seq"]` 只在无 `header.stamp` 时递增 → 真实 Gazebo 永远带 stamp，seq 恒为 1，飞控 `frame.seq <= _last_seq` 会丢弃首帧之后全部 IMU。改为每帧递增，stamp 只决定时间戳来源。② `gz` 后端 `--timeout` 原为整体运行 deadline（默认 5 s 到点必退），与文档「无进展超时」语义不符且长跑必挂，改成基于 `last_progress` 的 idle 超时。
- **修掉两个 SDF 的 XML 非法**：XML 注释内不允许 `--`；`homefly_quad.sdf` 与新建 world 注释里的 `--backend` / `--imu-topic` 会令整个 SDF 解析失败。改写措辞后两个文件均通过 `xml.etree` 解析。
- **脚本路径坑**：脚本最初用 `$ROOT` 绝对 POSIX 路径，Git Bash 把 `/d/Github/...` 传给 Windows 原生 `python.exe` 会错转成 `D:\d\Github\...`。改为脚本开头 `cd "$ROOT"` 且所有路径相对（`-S .`、`tools/...`、默认 `build/wsl`），Linux/WSL 与 Git Bash 通吃，分支更少。
