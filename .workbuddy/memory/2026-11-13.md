## 电机话题对齐收尾（GUI 可视化续）
- be2ad12 去掉 robotNamespace 后 GUI 日志仍显示 `No robotNamespace set using entity name.` + `Listening to topic: homefly/actuators` → 与 bridge 默认 `/actuators` 仍不匹配。
- 根因（查 gz-transport13 `TopicUtils.cc` / gz-sim `MulticopterMotorModel.cc` 源码确认）：
  * `AsValidTopic` 只清理字符，把 `//` 的**两个**斜杠一起跳过，且**不补前导斜杠** → 旧 `homefly//actuators` = `homeflyactuators`。
  * 缺 `robotNamespace` 时 gz 用**模型名**兜底 → `AsValidTopic("homefly/actuators")` = `homefly/actuators`（无前导斜杠）。
  * `FullyQualifiedName` 把非绝对 topic 规范化为 `/homefly/actuators`；bridge advertise `/homefly/actuators` 与之相同，`/actuators` 则永远不匹配。
- 修复：bridge `--motor-topic` 默认 `/actuators` → `/homefly/actuators`（help 注明与模型名绑定，改模型名要同步改）；world 顶部注释重写并消除 XML 注释里非法的 `--`；docs 4.1 / 8.5 修正 + 新增 8.7「WSLg GUI 三终端闭环」。
- **重要认知修正**：此前 headless `SITL run PASS` 只验证 FC↔bridge 的 UDP 闭环，Gazebo 电机插件从未收到 Actuators（飞机一直没被驱动）。GUI 场景必须单独用 `gz topic -e -t /homefly/actuators` + 视口里 rotor 转动来验证。
- FC 主循环 `for (step < options.steps)`，故 FC `--steps 0` 会立刻退出；bridge `--steps 0` 才是无限。GUI 命令里 FC 必须给正整数（如 30000）。
- 本地验证：py_compile + `--self-test` PASS；world XML 良构；`parse_args([]).motor_topic == /homefly/actuators`；按源码复刻的规范化推演证明两边 topic 一致。真实 GUI 三终端闭环待用户在 WSL 侧验证。
