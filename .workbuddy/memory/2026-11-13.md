## 电机话题对齐收尾（GUI 可视化续）
- be2ad12 去掉 robotNamespace 后 GUI 日志仍显示 `No robotNamespace set using entity name.` + `Listening to topic: homefly/actuators` → 与 bridge 默认 `/actuators` 仍不匹配。
- 根因（查 gz-transport13 `TopicUtils.cc` / gz-sim `MulticopterMotorModel.cc` 源码确认）：
  * `AsValidTopic` 只清理字符，把 `//` 的**两个**斜杠一起跳过，且**不补前导斜杠** → 旧 `homefly//actuators` = `homeflyactuators`。

  * `FullyQualifiedName` 把非绝对 topic 规范化为 `/homefly/actuators`；bridge advertise `/homefly/actuators` 与之相同，`/actuators` 则永远不匹配。
- 修复：bridge `--motor-topic` 默认 `/actuators` → `/homefly/actuators`（help 注明与模型名绑定，改模型名要同步改）；world 顶部注释重写并消除 XML 注释里非法的 `--`；docs 4.1 / 8.5 修正 + 新增 8.7「WSLg GUI 三终端闭环」。
- **重要认知修正**：此前 headless `SITL run PASS` 只验证 FC↔bridge 的 UDP 闭环，Gazebo 电机插件从未收到 Actuators（飞机一直没被驱动）。GUI 场景必须单独用 `gz topic -e -t /homefly/actuators` + 视口里 rotor 转动来验证。
- FC 主循环 `for (step < options.steps)`，故 FC `--steps 0` 会立刻退出；bridge `--steps 0` 才是无限。GUI 命令里 FC 必须给正整数（如 30000）。
- 本地验证：py_compile + `--self-test` PASS；world XML 良构；`parse_args([]).motor_topic == /homefly/actuators`；按源码复刻的规范化推演证明两边 topic 一致。真实 GUI 三终端闭环待用户在 WSL 侧验证。

## GUI + WiFi GCS 可视化遥控（--realtime pacing + --interactive）
- 用户要求「加 --wifi 把 GCS 接进来，在 GUI 里做可视化遥控」。
- **核心坑：两个时钟不同步**。`--gazebo` 下 FC 用 bridge 合成时间戳作仿真时钟
  （`GazeboClock` / `simulation_source.cpp`），`CommandReceiver` 拿同一个
  `source->clock()` 判 `--link-timeout` stale（`main.cpp:323`）；GCS 按**墙钟**
  20 Hz 发帧，bridge 默认以 UDP 允许的最快速度锁步推进（30000 步几秒墙钟跑完），
  两帧 GCS 之间在仿真时间里远超 timeout → FC 反复误判链路丢失并断臂。
- 修复：`tools/gazebo_bridge.py` 新增 `--realtime`，gz 锁步循环每帧按 `period_us`
  锚定墙钟节拍（掉队就 re-anchor、不补发积压帧灌进 FC 的 SPSC ring），使
  仿真时间 ≈ 墙钟时间。`tools/wifi_gcs.py` 新增 `--interactive`：daemon 线程读
  stdin 改 `live` dict，发送循环独占 socket/seq 按 `--rate` 持续重发；语法
  `roll/pitch/yaw/t/arm/disarm/q`。`docs/gazebo.md` 新增 8.8 四终端命令 + 验收标准。
- **两个同名 `--realtime` 别搞混**：4.1 表里的是 **FC 参数**，与 `--gazebo` 互斥、
  同时给会被忽略（终端 3 不要加）；8.8 的是 **bridge 参数**，必须加在终端 2。docs 已加 note。
- `q` 判断放在发送循环**发帧之后**：管道式 stdin 的 `q` 会被 reader 线程在首轮前
  消费，否则退出时 `sent 0`。极简位置调整，不改人工交互语义。
- **PASS 判据陷阱**：`main.cpp:624-627` 要求结束瞬间 `mode=Stabilize` 且
  `|roll|,|pitch| < 0.05 rad`，这是自稳回归判据不是遥控判据；打杆期间收尾会
  `FAIL` 属正常。想拿 PASS 要回中收敛，且**等 FC 打印 result 之后再输 `q`**
  （q 会发 DISARM 让 mode 变 Disarmed）。
- 本地验证：py_compile + bridge `--self-test` PASS；`parse_args` realtime
  default=False / explicit=True、period_us=1000、motor_topic=/homefly/actuators；
  管道 q 冒烟 `sent 1`、带延迟冒烟 `sent 105`；pacing 200 拍 0.233 s（Windows
  sleep 抖动，WSL2 更贴近 0.200 s，对 2 s link-timeout 无影响）。
- 四终端真实 GUI+WiFi 闭环待用户在 WSL 侧 `git pull` 后验证。

## ArduPilot 机场 / 迷宫场景接入
- 用户要求把 GUI 场景换成 ArduPilot 开发文档里的「机场 + 迷宫」无人机地图。
- **溯源确认**：
  * 迷宫 = `ArduPilot/ardupilot_gz` → `ardupilot_gz_gazebo/worlds/maze.sdf`：14 面墙全是内联 box + 一个 floor plane，**零外部依赖**（11.8 KB）。对应 ROS2 Cartographer 文档的 `iris_maze.launch.py`。
  * 机场 = `ArduPilot/ardupilot_gazebo` → `models/runway`：`model.sdf` 引用 `airfield.dae` + `runway.png` + 4 张 2K 草地 PBR 贴图，**合计 18 MB**（`Grass004_2K_NormalGL.jpg` 单张 10 MB）；`runway.sdf` 只是 `<include>model://runway</uri>` + pose `(-29 545 0 0 0 363)`。该模型本身没有机库/塔台 3D 几何，只是跑道平面 + 草地平面。
  * `ArduPilot/SITL_Models/Gazebo/worlds/` 里全是 `*_runway.sdf` / `*_playpen.sdf`，没有 maze；`ardupilot_gz_description/models` 也没有 runway 模型。
- **决策**：不引入 18 MB 二进制进飞控仓库。迷宫逐字复制上游几何；机场按上游跑道布局用内联 `<box>` + 纯色材质重建（跑道/中心线/阈值条/停机坪/机库/塔台/风向袋/油罐），装饰模型只有 `<visual>` 无 `<collision>`，避免干扰 IMU。
- **关键契约（务必保持）**：三个 world 都用 `world name="quad"`（IMU 话题 `/world/quad/model/homefly/link/body/sensor/imu/imu`）与 `model name="homefly"`（电机插件靠模型名兜底 → `homefly/actuators` → `/homefly/actuators`）。**改任一名即断链**。`homefly` 模型从 `homefly_quad.world` 逐字复制，physics 1 ms/1 kHz、IMU、4 个 `MulticopterMotorModel`、link 集合全一致，故 8.7/8.8 的 PASS 结论可迁移。
- 迷宫把停机点从 `(0,0,0.2)` 移到较开阔的 `(2,2,0.2)`（原点 1 m 内就有 x=-1/y=-1 两面墙）；墙**带 collision**，打杆过猛撞墙会产生异常 accel 触发 `InvalidImuData` 粘性 Failsafe，纯净姿态回归仍用默认 world。
- `run_wsl_sitl.sh` 早已有 `--world PATH`（第 26/59 行），GUI 只需换终端 1 的 world 路径，桥接/FC/GCS 命令零改动。
